========================================
BCD -> DECIMAL  (DS3231 time reading)
========================================


1. THE PROBLEM (why numbers looked wrong)
------------------------------------------
When reading seconds from the DS3231, the screen showed junk:
counting past 59 (like 71, 80, 89), skipping numbers, etc.

Root cause:
   - The DS3231 STORES and SENDS its values in BCD.
   - Our microcontroller READ those 8 bits as a plain binary number.
   - BCD read as plain binary = the wrong number.

The DS3231 did nothing wrong. The bug is on OUR side: we have to
DECODE the BCD byte back into a real decimal number before using it.


2. WHAT BCD ACTUALLY IS
-----------------------
BCD = Binary Coded Decimal.
Each DECIMAL digit is stored separately in its own 4-bit half of the byte.

Example: the number 23
   tens digit = 2  ->  0010
   ones digit = 3  ->  0011
   packed byte     ->  0010 0011   (this is 0x23)

Key point: in hex, BCD "looks like" the decimal number.
   45 seconds  ->  0x45
   59 seconds  ->  0x59
That's the whole point of BCD: clean, human-readable digits.


3. WHY IT BREAKS WHEN READ AS PLAIN BINARY
------------------------------------------
The byte 0x23 read as a normal number is NOT 23. It's:
   0x23 = (2 x 16) + 3 = 35

So "23 seconds" printed as 35. And "59 seconds" (0x59) printed as:
   0x59 = (5 x 16) + 9 = 89

That's why the count went past 59 and skipped numbers -
certain hex combos (like 0x0A-0x0F) never occur in BCD, so the
plain-binary version skips those decimal values.


4. THE FIX: DECODE BCD -> DECIMAL
---------------------------------
A BCD byte has two halves:
   upper 4 bits = tens digit
   lower 4 bits = ones digit

To rebuild the real number:  (tens x 10) + ones

Two bit operations do the splitting:

   TENS:  byte >> 4
          Slides the top 4 bits down into the bottom.
          0010 0011  >> 4  =  0000 0010  = 2

   ONES:  byte & 0x0F
          Mask keeps the bottom 4 bits, zeroes the top.
            0010 0011
          & 0000 1111
          -----------
            0000 0011   = 3

Then combine:  (2 x 10) + 3 = 23


5. THE DECODER FUNCTION
-----------------------
uint8_t bcdToDec(uint8_t byte){
    uint8_t tens = byte >> 4;    // slide top 4 bits down
    uint8_t ones = byte & 0x0F;  // keep bottom 4 bits
    return (tens * 10) + ones;   // rebuild real decimal
}


6. TWO SEPARATE JOBS (don't confuse them)
-----------------------------------------
   bcdToDec()     fixes the NUMBER     (0x23 byte  ->  real 23)
   printNumber()  splits for DISPLAY   (23  ->  chars '2' and '3')

You need BOTH, in this order: decode first, THEN print.

Reminder on printNumber: UART sends ONE char at a time, so we split
a number into digits with:
   tens = num / 10;   ones = num % 10;
   send (tens + '0'), then (ones + '0');   // +'0' turns digit into a character
This split only works if num is already a NORMAL decimal (0-99) -
which is exactly why bcdToDec must run first.


7. QUICK SELF-TEST
------------------
Byte 0x45 (BCD for 45):
   >> 4    = 0000 0100 = 4   (tens)
   & 0x0F  = 0000 0101 = 5   (ones)
   (4 x 10) + 5 = 45   correct
